# Modelo de dados — Fase 0

Schema completo em [`prisma/schema.prisma`](../prisma/schema.prisma). 24 tabelas (13 da Fase 0 + `permuta`, `usuario`, `sessao`, `empreendimento_usuario`, `indice_correcao`, `distrato`, `financiamento_producao`, `destinatario_comissao`, `renegociacao_venda`, `desembolso_custo` e `contraparte_permuta`, adicionadas na Fase 1), todas genéricas — nenhuma coluna ou valor específico de um empreendimento. O que muda entre o Splendido e qualquer outro empreendimento são as **linhas**, nunca a tabela.

Convenção: todo valor monetário ou percentual é `String` (texto decimal), nunca `Float`. Ver `docs/ARQUITETURA.md`, princípio B.

| Tabela | Finalidade | Observação |
|---|---|---|
| `empreendimento` | Raiz de tudo | `incorporador` é um campo texto simples nesta fase (achado da revisão: multiempresa real não é necessária ainda — só multiempreendimento) |
| `cenario` | Base/otimista/pessimista/personalizado | `horizonteProjecaoMeses` é obrigatório e nunca hardcoded em nenhum outro lugar do sistema; `limiteNecessidadeMaximaCapital` (Fase 1, achado F15) é opcional — nulo usa o padrão de 30% do motor de alertas, por cenário (não por empreendimento), já que cenários base/otimista/pessimista legitimamente toleram riscos diferentes; `dataMesUm` (Fase 1, achado F27) é opcional — âncora de calendário para "mês 1", usada só pela conciliação de extrato bancário; nenhum "mês" do sistema tem calendário além dela |
| `terreno` | Uma matrícula/registro de área — 1:N com empreendimento desde a Fase 1 (achado F26) | `areaStatusValidacao` (`pendente`/`validado`/`conflitante`) + `areaObservacao` registram divergências de fonte em vez de escondê-las (ver Splendido: conflito SÍNTESE×LEGAL); `numeroMatricula` (Fase 1) identifica cada matrícula quando há mais de uma |
| `tipologia` | Produto (ex.: "1 Quarto", "Loja") | Cadastro livre, sem lista fixa |
| `unidade` | Unidade física vendável | `precoVenda` é um valor direto na linha — sempre foi assim, inclusive quando calculado por cascata de andar (Fase 1, achado F2): a estratégia de precificação decide o número no momento da criação, o schema nunca soube que existia mais de uma estratégia |
| `permuta` | Cadastro nominal de quem recebeu uma unidade permutada | 1:1 com `unidade` (achado F3/F4); nunca lida pelo motor — `Unidade.status='permutada'` já é suficiente para excluir a unidade do VGV |
| `contraparte_permuta` | Permuta parcial — quem mais divide a mesma permuta com a contraparte principal (Fase 1, achado F24) | 1:N com `permuta`; nunca lida pelo motor, mesmo espírito de `destinatario_comissao` (achado F13) — a soma de `percentualSplit` de uma permuta nunca pode ultrapassar 100%, validado na API |
| `condicao_pagamento` | Agrupa modalidades | 0 ou 1 por tipologia (ou pode ser por empreendimento, se `tipologiaId` for nulo) |
| `modalidade_pagamento` | Uma fatia da condição (ex.: "Entrada") | `tipoDistribuicao` é o campo que generaliza o motor — ver `REGRAS_DE_NEGOCIO.md` |
| `premissa_velocidade_vendas` | Quantas unidades/mês/tipologia se espera vender | Consumida por `gerarVendasDePremissaVelocidade()` para criar `Venda` reais |
| `venda` | Uma unidade vendida em um mês | Gatilho do motor de recebimentos |
| `recebimento_projetado` | Saída do motor — um evento de caixa futuro | O campo `valorPrevisto` é sempre regenerado a partir de `venda` + `modalidade_pagamento`; `valorRealizado`/`status` são dado real registrado pelo usuário (Fase 1) e preservados entre recálculos — chave `(vendaId, modalidadeId, mesCompetencia)` única garante que o `id` da linha não muda a cada recálculo (achado F4, `docs/DECISOES.md`) |
| `categoria_custo` | Categoria + tipo de incidência | `empreendimentoId` nulo = categoria reutilizável entre empreendimentos |
| `custo` | Uma linha de custo/despesa | `participaFluxoCaixa` decide se entra no fluxo — é o mecanismo do achado F/4.3; `valorRealizado`/`status` (Fase 1) só fazem sentido para custos de incidência fixa, que têm um mês de competência único; `tipologiaId` (Fase 1, achado F11) é um escopo opcional — sem ele, incide sobre todas as vendas do cenário (comportamento original); preenchido, só sobre as vendas daquela tipologia, permitindo comissões diferentes por produto sem tabela nova; `grupoIndiceCorrecao` (Fase 1, achado F20, padrão `"padrao"`) escolhe qual série de `indice_correcao` corrige este custo |
| `cronograma_fisico_financeiro` | % de execução física por mês | Curva livre, sem formato pressuposto (não precisa ser "S") |
| `usuario` | Login e permissão (Fase 1) | `senhaHash` via `bcryptjs`; `papel` (`admin`/`usuario`) é a dimensão de permissão por ação — ver `empreendimento_usuario` para a dimensão de permissão por empreendimento |
| `sessao` | Token de sessão ativo (Fase 1) | Token opaco (não JWT), verificado a cada request; revogar é apagar a linha |
| `empreendimento_usuario` | Vínculo de acesso usuário×empreendimento (Fase 1, achado F5) | Só existe para `papel='usuario'` — `admin` nunca é restringido por ela; sem vínculo, um `usuario` não vê o empreendimento na listagem e recebe 404 (não 403) ao tentar acessá-lo direto. `papel` do vínculo (Fase 1, achado F23, padrão `"edicao"`) é uma dimensão independente do `usuario.papel` global — `"leitura"` bloqueia qualquer método != GET nas rotas escopadas a esse empreendimento |
| `indice_correcao` | Série de variação mensal de índice de correção monetária, por cenário e por grupo (Fase 1, achado F6; estendida a custos no achado F12; múltiplas séries por grupo no achado F20) | `grupo` × `mes` × `percentual` (pode ser negativo — deflação), `@@unique([cenarioId, grupo, mes])`; `grupo` é texto livre (`"padrao"` por omissão) — um cenário pode ter mais de uma série (ex.: "obra" corrigida por INCC, "padrao" por IGP-M); nunca lida diretamente pelo motor — `src/core/motorCorrecao.ts` aplica o fator acumulado por cima, sempre recomputado, nunca persistido em `recebimento_projetado` nem em `custo` (mesmo padrão do achado F1). Recebimentos sempre corrigem pela série "padrao" (usando o mês da venda como mês-base, um por venda) — só `custo.grupoIndiceCorrecao` pode escolher outra série; custos usam um mês-base fixo (mês 1) para todo o cenário — orçamento de obra é fixado uma única vez, não por linha de custo |
| `distrato` | Registro nominal do cancelamento de uma venda (Fase 1, achado F7) | 1:1 com `venda` (`vendaId` único); nunca lido pelo motor — `Venda.status='distratada'` (existente desde a Fase 0) já é suficiente, o motor só busca vendas `status="ativa"`. Guarda `valorRecebidoAteDistrato`/`percentualRetencao`/`valorRetido`/`valorReembolsar`, calculados sobre o valor **realizado**, nunca o previsto |
| `renegociacao_venda` | Distrato parcial — registro nominal de uma redução do valor de uma venda ativa (Fase 1, achado F17) | 1:N com `venda` (pode haver mais de uma ao longo do tempo); nunca lido pelo motor — a ação em si é atualizar `Venda.valorVenda` diretamente, o motor sempre lê esse campo do banco a cada recálculo. Guarda `valorVendaAnterior`/`novoValorVenda`/`motivo`, puramente para auditoria |
| `financiamento_producao` | Financiamento bancário de produção, por cenário (Fase 1, achado F8; tabela de amortização no achado F16) | 1:1 com `cenario` (`cenarioId` único); diferente de `indice_correcao`, É lido pelo motor — liberações (curva do cronograma físico) e amortização entram na consolidação real do fluxo de caixa, não ficam ao lado dela. `tipoAmortizacao` (`unico`/`sac`/`price`, padrão `unico`) decide como o saldo devedor acumulado até `mesAmortizacao` é pago de volta — de uma vez, ou em `numeroParcelas` parcelas |
| `destinatario_comissao` | Cadastro nominal de quem recebe a comissão de um custo, e como ela se divide (Fase 1, achado F13) | 1:N com `custo`; nunca lido pelo motor, mesmo espírito de `permuta`/`distrato` — puramente informativo. Não restrito a uma `tipoIncidencia` específica (diferente do escopo por tipologia do achado F11): split nominal é controle do usuário, não regra de cálculo. A soma de `percentualSplit` de um custo nunca pode ultrapassar 100%, validado na API |
| `desembolso_custo` | Uma parcela mensal computada pelo motor para um custo de incidência percentual, com seu próprio realizado (Fase 1, achado F21) | 1:N com `custo`, `@@unique([custoId, mes])`; mesmo padrão de `recebimento_projetado` — `valorPrevisto` sempre regenerado pelo motor a cada recálculo (upsert por chave, nunca delete+recreate, para o `id` não mudar sob uma ação "marcar como pago" em andamento), `valorRealizado`/`status` são dado real do usuário, preservados entre recálculos. Só existe para custos não-`fixo` — `custo.valorRealizado` continua servindo os custos fixos (mês de competência único), sem sobreposição entre as duas |

## O que foi deliberadamente deixado de fora da Fase 0

Ver `docs/DECISOES.md` para a justificativa de cada item — nenhum foi esquecido, todos foram avaliados e adiados conscientemente:

- `MovimentoCaixa` — **removida como tabela**, é serviço computado (achado F1)
- `FinanciamentoProducao`, `AlertaRisco`, `SimulacaoSensibilidade`, `VersaoCenario`, `EstruturaComissao`, `IndiceCorrecao`, `Distrato` — todas fora do MVP definido, sem impacto no motor financeiro

Itens desta lista original já foram implementados na Fase 1 (ver `docs/FASES.md`): `Permuta` (cadastro nominal, achado F3), a cascata de preço por andar (achado F2, sem tabela nova — ver `src/core/precificacaoAndar.ts`), `Usuario`/`Sessao` (login e permissão por ação), `EmpreendimentoUsuario` (permissão por empreendimento, achado F5), `IndiceCorrecao` (correção monetária, achado F6), `Distrato` (achado F7), simulação de sensibilidade (sem tabela nova — ver `src/core/motorSensibilidade.ts`), `FinanciamentoProducao` (achado F8), `AlertaRisco` (achado F9, sem tabela nova — ver `src/core/motorAlertas.ts`), versão de cenário (achado F10, sem tabela nova — reaproveita `Cenario.derivadoDeCenarioId`, que já existia desde a Fase 0), estrutura de comissão (achado F11, sem tabela nova — `Custo.tipologiaId` opcional sobre o mecanismo genérico existente) e `RegistroAreaTerreno` (achado F26 — `Terreno` deixou de ser 1:1 e virou 1:N, com `numeroMatricula`, em vez de introduzir um modelo novo). A lista original está esgotada.
